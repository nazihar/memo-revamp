# E06 Visual workflow builder — threat model

STRIDE over the builder, the simulation and the review diff. ASVS 5.0 references are in brackets. The builder is a client of the E03 definition API. Every rule that protects definitions is enforced on the server and stays there: permissions, maker-checker, If-Match, schema and semantic validation, and the condition sandbox. The browser only proposes a body.

| # | Threat | Flow | Mitigation | ASVS |
|---|---|---|---|---|
| S1 | Someone without the authoring permission edits a definition through the builder | edit, save | The builder calls the existing endpoints. `workflow.definitions.manage` guards draft changes and validation, and `.approve` guards review (deny by default). The menu and buttons follow the same permissions, but the server decides | V8.1.1, V8.2.1 |
| T1 | The reviewer approves something other than what the diff showed | review | The diff compares the two **stored** bodies the server returns: the version in review and the published one. A version in review cannot change, because only drafts accept a body, so the reviewer approves exactly what they read. Approval needs a step-up | V2.3.1, V8.2.3 |
| T2 | A crafted body bypasses the builder's forms (hand-edited JSON, a scripted request) | save | The server validates every body against the JSON Schema and the semantic checks on save, submit and approve. The builder's forms are a convenience, not a control. The JSON view stays as the expert path and goes through the same checks | V2.2.1 |
| T3 | Two authors overwrite each other's work | save | Saves carry If-Match (the version's revision). A stale save returns 412 and nothing is lost: the builder keeps the local graph and offers to reload or copy it | V2.3.3 |
| T4 | A condition does something other than compare attributes | condition | Conditions are CEL in the E03 sandbox (ADR-0039). Only declared attributes are allowed, there is a cost limit, and they are compiled on the server. The condition editor writes CEL text; it never evaluates it | V1.3.2 |
| R1 | Nobody can tell who changed a definition, or what changed | save, review | Each draft save, submit, approve and send-back is audited (`workflow.definition.*`, ids only), and the stored versions keep every body. The diff can be rebuilt from any two versions at any time | V16.2.1 |
| I1 | Simulation reveals people or memo content to someone who should not see them | simulate | Only holders of `.manage` or `.approve` may simulate, and they already see the organisation. Simulation uses **sample** attributes and never reads a memo. It shows the names of the people who would be resolved, exactly as the DoA simulator (E04) does | V8.2.2, V14.2 |
| I2 | Simulation is used to map who holds which position at scale | simulate | It is read-only and needs a privileged permission. A new per-user rate limit (`RateLimit.WORKFLOW_SIMULATION_PER_USER`, the platform's Bucket4j limiter, ADR-0025) caps runs. One run returns at most one path | V2.4.1 |
| D1 | Validation or simulation runs on every keystroke and loads the server | validate, simulate | Validation is debounced in the browser (about 500 ms after the last change, one request in flight, stale answers dropped). Simulation runs only on request and has its own per-user limit; validation gets one too, generous enough for typing. Bodies stay within E03's limits: 1 MiB and 100 steps | V2.4.1 |
| D2 | A definition makes the simulation run forever | simulate | The simulation refuses invalid bodies before it starts. It applies at most 500 commands in one run and stops with `SIMULATION_LIMIT` | V2.4.2 |
| E1 | Text in a definition (a step name, a note, a message key) runs as script in another admin's browser | canvas, diff | React escapes all text. The canvas and the diff render names as text nodes only. A lint rule added in T1 (`no-restricted-syntax` on `dangerouslySetInnerHTML`) forbids raw HTML; none is used today. The CSP forbids inline script (Phase 1a) | V3.2.2 |
| E2 | Maker-checker is bypassed by approving one's own version from the builder | review | Unchanged from E03: the server refuses an approval by the submitter (`SAME_PERSON`). The builder hides the approve action from the submitter, but the server decides | V8.2.3 |
