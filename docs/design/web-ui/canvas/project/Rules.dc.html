Memo & Meetings · web app

Design rules

Default shadcn/ui components on the neutral palette, kept compact. Every screen follows these rules. To do something new, change the rule here first, then the screen.

1. Principles

Compact, not cramped 32px controls and 14px text on desktop; 44px touch targets on phones.
One primary action per view The dark button is the thing this person came to do. Everything else is outline, ghost or in a menu.
Same job, same place Filters above lists, decisions top right (bottom bar on phones), page actions beside the title.
The server is the truth Show only actions the API allows and counts the API returns. Hide, don't disable, what a person may never do.
Build with shadcn/ui components, not hand-written markup These screens are hand-written HTML only because the canvas cannot run React. In the app, every control is a shadcn/ui component in components/ui, themed with the colour tokens below. Do not copy the canvas’s inline styles. If a component is missing, add it with npx shadcn@latest add <name> before writing anything of your own. The app already has Button, Badge, Dialog, DropdownMenu, Field and Toast; add the rest.

2. Colour tokens

Use the token, never a raw hex. Names match web/src/styles/tokens.css; values move to shadcn neutral. Theme follows the system by default; every screen is checked in both themes.

Tenant branding may replace --primary only if it keeps 4.5:1 contrast with --primary-foreground; otherwise the brand colour is used for the logo only.

Chart colours

Charts get their own colours, separate from the interface tokens above. Hues are assigned in this fixed order and never cycled; a colour follows its series, so filtering never repaints what is left.

Token Light Dark Use for
--series-1 #2a78d6 #3987e5 First series, and the only colour of a single-series chart (pending by age, created, median)
--series-2 #eb6834 #d95926 Second series (completed, P90)
--critical #d03b3b #d03b3b Status only: overdue. Always with an icon or a label, never as a third series
Colour rules
  • Blue then orange pass the colour-blindness and contrast checks in both themes (worst pair ΔE 24.7 light, 26.8 dark). Check any new colour with the palette validator before using it.
  • More series take the next hues of the validated order (aqua, yellow, magenta, green, violet, red), checked again. Past eight, group the rest into “Other” or split into small charts.
  • Text is never in a series colour: values, labels and legends use the text tokens, with a coloured mark beside them.
  • Status colours (good, warning, serious, critical) are not series colours and always come with an icon and words.
Marks and reading aids
  • Bars at most 24px thick, 4px rounded at the value end, square at the baseline; a 2px gap between touching segments.
  • Lines 2px; dots at least 8px with a 2px ring in the page colour. Grid lines are 1px hairlines in --hover.
  • One value axis per chart, never two. Two measures on different scales are two charts.
  • Two or more series always have a legend; a single series is named by its title. Label sparingly: line ends, bar tips, never every point.
  • Every chart has a hover tooltip and a Show as table button, so nothing depends on colour or hovering alone.

Memo pages
  • Every memo page you read (in review, returned, approved, rejected, withdrawn, cancelled, discarded, closed) has the same parts in the same order: header, outcome bar once it has ended, tabs, and a right column.
  • Outcome bar colour: green for approved, red for rejected, neutral grey for withdrawn, cancelled, discarded and closed. Ended pages then show the reason or remark when one was given, and what you can do next (a follow-up memo; for a discarded draft, a new memo, since it cannot be linked).
  • Tabs, always these and always in this order: Overview, Note sheet, Attachments, Linked memos, History. Counts only on tabs that have items; an empty tab says what will appear there.
  • Overview starts with what the reader came for: the decision to make, the final record, or the reason it was rejected. Then the document and the details.
  • The right column holds the task or the approvals, then people and access. Nothing else. For the initiator of a memo in review, the task card becomes “Waiting for approval”: who has it now, Recall while nobody has acted in the round, and Withdraw.
  • A memo you have opened before starts its overview with “Since you last looked” when anything changed. Opened from My tasks, its header shows the position (“1 of 7”) with previous and next, and every decision dialog offers “Open my next task after this”.
  • Only the draft uses stacked sections instead of tabs, because the document, approvers and details must be visible together while preparing it.
  • Imported memos follow the same layout with what they have: tabs Overview, Original documents, Linked memos, History; a neutral “not verified by this system” bar; legacy approvals in the right column. No note sheet, decisions or final record.
  • On phones every memo page is one column: header, the main card, then rows that open the note sheet, attachments, linked memos and history.

6. Components

Buttons
  • Destructive only for the action that ends something (Reject, Discard), and only inside its confirm dialog. On the page it is outline with red text.
  • Secondary actions beyond two go in a "⋯" menu, each with a one-line hint.

⊕ Facet filter Sort: Due first
  • Tabs switch views of the same thing; counts only when the server returns a total.
  • Filters are dashed buttons that show their chosen value; sort is a solid button that names its order.
Lists and tables
  • Desktop: a table in a bordered box; 40px header in muted text; rows two lines at most (title, then reference · round in 12px).
  • The whole row opens the item; checkboxes and "⋯" do not.
  • Load more with Show more (cursor). Never page numbers or rows-per-page.
  • Unread rows: a blue dot before the subject and a semibold subject, with “Unread” for screen readers. Never colour alone.
  • Codes (sign-in, step-up, setting up the authenticator) are six boxes in two groups of three (InputOTP). One real input underneath takes typing, paste and the phone’s one-time-code autofill; the boxes only show it.
  • States: skeletons, not spinners, in the shape of what is loading. Empty says what will appear and offers the one action that fills it; with filters on, offer Clear filters. Errors give a plain title, the reference for support and Try again; if only one section fails, only that section shows it. A missing memo and one you may not see read the same: “This memo does not exist, or you cannot see it.” See the Page states row.
  • Every page uses the full content width: lists, settings (My security, Notification settings), dashboards. The one exception is a page that is a single form from top to bottom (New memo), capped at 760px. Inside full-width pages, single fields keep their own sensible width (about 360px) instead of stretching.
  • Phone: a list, not a table. Title (two lines max) with the due badge on the right, then reference · type, then action · sender · relative time.
  • Selection: always-visible checkboxes on desktop; a Select mode on phones. Bulk actions appear in a dark bar at the bottom; decisions are never bulk.
Menus, dialogs, sheets
  • Short forms (up to about three fields: change password, rename, reassign, save a search) open in a dialog on desktop and a bottom sheet on phones. Never expand a form inside a card or a list row: it pushes the page around. Only a page that is one long form (New memo) is a page of its own.
  • Menus close on Esc and on a click outside; keyboard focus returns to the button that opened them.
  • Every decision opens a confirm dialog (a bottom sheet on phones) that says what happens next and takes a remark: optional for approve, required for return and reject.
  • Dialog widths: 460px for a short form, 560px when it holds a list or an editor, 900px for previews and comparisons. Title 18px, description, fields, then Cancel and the action on the right.
  • Errors stay inside the dialog or sheet, never in a toast behind it. A problem with one field shows under that field (red border, short message). A problem with the whole form (it changed meanwhile, something inside must close first, it did not work) shows as a red alert above the fields. Keep what the person typed; the dialog stays open.
  • Validation is form validation, not HTML validation. Every form sets noValidate; inputs carry no required, pattern, min/max or email checks that make the browser show its own bubbles. The form (TanStack Form, already in the app) checks the values on submit, then again as the person types in a field that already shows an error. Messages are ours and short ("Required.", "Those dates do not fit."), shown under the field with aria-invalid and aria-describedby, and focus moves to the first field with an error. The submit button stays enabled and says what is missing instead of greying out. Refusals from the server go on the field they concern, otherwise in the alert above the fields.
Empty, loading, error
  • Empty: icon tile, one-line title, one sentence on what will appear here. Add a button only when it creates the missing thing.
  • Loading: skeleton rows at the real row height; never a full-page spinner.
  • Error: say what failed and offer Retry; keep what was already loaded on screen.

7. Words, dates, numbers

  • Buttons are plain verbs that name the outcome: Approve, Return, Show more. Not "Submit decision" or "Click here".
  • Sentence case for everything, including titles and tabs.
  • All copy goes through react-intl; the same action uses the same word on every screen.
  • Tenant terms (memo, forum) come from the Language and terms settings, never hard-coded.
  • Desktop tables: "16 Nov, 14:20". Phone lists: relative ("Yesterday", "3 days ago"), exact time on the detail screen.
  • Due: "Overdue 1 day", "Due tomorrow", "Due in 3 days", then "Due 28 Nov".
  • Amounts with currency code and grouping, tabular numbers: BDT 250,000,000.
  • References in Geist Mono: CR/2026/0142.

8. Accessibility (WCAG 2.2 AA)

  • Real buttons and links; never click handlers on divs.
  • Text contrast at least 4.5:1, including grey meta text, in both themes.
  • Status is never colour alone: every badge has words.
  • Visible focus: 3px ring in --ring at 50%.
  • Tabs use arrow keys; menus and dialogs trap and return focus.
  • Logical properties only (start/end), so layouts mirror for right-to-left languages.
  • Touch targets 44px on phones; 24px minimum anywhere.
  • Every icon-only button and checkbox has an accessible name that includes the item ("Select Q4 branch expansion budget").
