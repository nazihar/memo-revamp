- **T1 engine core:** `com.memo.workflow` (shared enums) and `com.memo.workflow.engine` (`Model`, `Commands`, `Guards`, `Transition`): a pure transition function over the instance state, with refusals instead of exceptions and the effects the service will write. `TransitionTest` (each allowed and forbidden transition), `WorkflowInvariantProperties`: 1,000 random scripts of up to 30 actions by random people (jqwik statistics require every final status and round 2 at least 10 times each; the first version of the generator never reached round 2 or 3, which the coverage check caught), plus a targeted property of up to six return-and-resubmit cycles proving only the last round's approvals count, `ArchitectureRulesTest` (the engine depends only on `java.lang`, `java.util`, Kotlin and the workflow API). PIT 1.30.1 through the Gradle plugin 1.19.0 on `com.memo.workflow.engine`, threshold 70 %, as a nightly job (replaces the placeholder); first run 90 % killed (113 of 125), test strength 95 %, line coverage 298 of 299; the survivors that mattered led to four extra assertions. `docs/dependencies.md` updated.
- **T2 workflow persistence and service:** `workflow/V1__engine.sql` (seven tables under forced RLS; `workflow_action` append-only by trigger and revoked privileges; one open round per instance, one open task per step and one instance per subject enforced by unique indexes); jOOQ regenerated. `Workflows` (public facade) → `WorkflowRunner` (lock, decide, write) → `InstanceStore` (read, lock) and `InstanceWriter` (guarded writes, gapless `seq`), `ActionEffects` (audit, events), `DefinitionStore` + bootstrap (built-in `sequential-approval` v1 per tenant, new and existing), `WorkflowSettings` (`workflow.route.max`, default 20). Events carry ids and enums only (`TaskClosure` instead of a state string, caught by `EventPayloadRulesTest`). `WorkflowServiceIT` (7 tests) folds the planned `WorkflowServiceIT`, `ActionLogImmutabilityIT`, `ActionSeqIT`, `DefinitionSeedIT` and `DoubleActionIT`; the idempotency replay and actor tests move to T5, where the HTTP endpoints that take `Idempotency-Key` arrive. Design §7 changed: submit, resubmit and withdraw are audited by the workflow module, not again by the memo.

## 2026-11-10
- PR #33 (Phase 2 plan) merged on the owner's word; PR #34 retargeted to `master`. Its first CI run had failed on SpotBugs (`SF_SWITCH_NO_DEFAULT`): Kotlin compiles a `when` over a sealed type with an empty `else` into a type switch without a default. `ActionEffects.publish` now maps the effects with casts.
- **T3 memo types and drafts:** permissions `memo.create` (built-in user role, so every active user), `memo.types.manage` and `workflow.tasks.reassign` (privileged). `common.authz.Clearances` (`rankOf(users)`, `levels()`, `level(id)`, `lowest()`) implemented by `authz` from the per-user grants cache, so clearance changes apply at once. `memo/V1__memo.sql`: `memo_type`, `memo`, `memo_route_entry`, `memo_participant` and `memo_reference_counter`, all under forced RLS. "General memo" is seeded per tenant (new tenants and, at start-up, existing ones). `Memos` (create, view, edit with `If-Match`, discard), `MemoTypes` (admin list, create, edit; the last active type cannot be deactivated), `MemoViews`, `MemoDocumentPurpose` (`memo.document`: DOCX only, record storage, audited reads; initiator only, and only while the memo is a draft or returned, which is also the review lock T5 needs) and `MemoDocumentListener` (records the document on its first version under the memo's row lock; vetoes a second file or an upload that lost a race with submit). Authorisation matrix `p2-e01-memo.yaml` started (T10 adds the per-participant subjects).
- Design changes, recorded in design §2 and §5: memos get a **reference** (`M-2026-00042`, numbered per tenant and calendar year in UTC; emails will carry it instead of the subject). A memo type's default classification may be null, meaning the tenant's lowest level, so seeding does not depend on the order of the authz and memo bootstraps. Edits are `PUT` with the whole field set, as everywhere else in the API, not `PATCH`. A memo cannot be classified above its initiator's clearance (they would lose it), refused as `above-clearance`. `origin_unit_id` stays null until the org module offers a user's primary unit.
- Known limitation: `memo.classification_rank` is a copy (design §6); if a tenant admin reorders classification levels, existing memos keep their old rank. Reordering is rare and admin-only; a re-rank listener is noted for Phase 3.
- The web's permission labels for the three new permissions come with the memo screens (T9); until then the role editor shows their keys.
- **T4 route and submit:** `PUT /memos/{id}/route` (whole list, `If-Match`; per-entry `self`, `duplicate`, `approver-inactive`, `approver-not-cleared`, and `empty` / `too-long` for the list), `POST /memos/{id}/submit` (document and route checked again under the memo's row lock), the memo's `WorkflowSubject` (blocked reasons from identity status and clearance; snapshot = document version id, number and SHA-256; veto of a round without a document), and `MemoWorkflowListener` (memo status, round and instance from `WorkflowActionTaken`; approvers become participants from `WorkflowTaskCreated`). The route limit is the workflow's `workflow.route.max` (default 20), exposed as `Workflows.maxApprovers()`; there is no separate `memo.route.max`.
- **T5 approver actions and rounds:** `POST /tasks/{id}/approve|return|reject`, `POST /memos/{id}/resubmit|withdraw`, all with an `Idempotency-Key` bound to the actor, answering with the memo view (now with `holders`, `myTask` and the approver's or initiator's allowed actions). Approval step-up: new security setting `security.stepup.approval.minutes` (default 30, 5–240) and `StepUpCheck.require(window)`; only approve asks for it, and only when the memo's type says so. A task on a memo the actor cannot see answers 404; a visible task someone else holds, 403. Found while writing it: approve locked the instance and then the memo row, withdraw the memo and then the instance, so the two could deadlock. `WorkflowSubject.lock(subjectId)` now runs before the instance lock for every action, and the memo locks its row there. Engine refusals map to HTTP in one place (`WorkflowProblems`).
- **T6 reassignment and blocked tasks:** `GET /admin/workflow/tasks?filter=open|blocked&assignee=` and `POST /admin/workflow/tasks/{id}/reassign` (`workflow.tasks.reassign`, fresh step-up, reason required; the engine refuses the same person, the initiator, someone already on the round and anyone not eligible). Subjects provide `summaries(ids)`; an administrator not cleared for a memo sees its reference but not its title. New partial index `workflow_task_open_idx` (`workflow/V2`).
- **T7 inbox, boxes and history:** reads moved to `WorkflowQueries` (`viewOf`, `subjectOfTask`, `myTasks`, `openTasks`, `holders`, `history`); keyset cursors shared in `common.web.Cursors`. `GET /inbox/tasks` (restricted placeholder when the reader may no longer see the memo), `GET /memos?box=drafts|sent|closed` (holders in one batch; discarded drafts are closed), `GET /memos/{id}/history` (by round, newest first, earlier rounds marked, each action with its document number and hash). `MemoPerformanceIT` generates 10,000 memos in review in SQL (300 tasks for the reader, 500 sent by them).
- **T8 notifications:** category `WORKFLOW` (not mandatory) and the seven kinds with English and Arabic emails that carry the reference and a link only. `WorkflowTaskCreated` and `WorkflowTaskClosed` now name the action that caused them, so a reassignment is told apart from an assignment. `AccessAdministration.tenantWideHolders(permission)` finds who to tell about a blocked task. `MemoNotifier` listens in the action's transaction.
- Other changes made on the way: `FileVersionCreated` is a `TenantScopedEvent` (its `purpose` field became `purposeKey`, as event fields must be ids, keys or codes); the table-naming rule (`RlsMetaTest`) accepts a table named exactly after its module (`memo`).
- Found by T8's tests: the Phase 1a `notification_item.link` check used the regular expression `{0,499}`, beyond PostgreSQL's limit of 255 repetitions, so any notification with a link failed (none had a link before). Fixed in `notification/V3__notification_link_check.sql` (length check plus `*`), with a regression test in `NotificationsIT`.
- **T9 web screens:** `features/memo`: inbox with tabs in the address (`/inbox?tab=`), create, memo view (document with upload of new versions, route editor with the people picker and ↑ ↓, history by round with earlier rounds marked, action bar fixed at the bottom on phones), one action dialog for the seven actions (key made when it opens, approve through the existing step-up handling, full-screen on phones), edit dialog, admin open tasks with reassignment, memo types. Navigation entries, permission labels, notification texts, mail-log and preference labels for the workflow kinds. `FileUpload` can send a new version (`If-Match`). Vitest: inbox (restricted placeholder), memo view (history, toolbar), return dialog (remark required, one key).
