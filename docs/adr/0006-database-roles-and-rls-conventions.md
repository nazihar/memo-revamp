# 0006 — Database roles, RLS policy conventions and tenant-context semantics

## Context and problem statement
`AGENTS.md §3.2` makes tenant isolation through PostgreSQL RLS non-negotiable. This ADR fixes the concrete roles, the policy form and how the application sets tenant context, so that every module does the same thing and a catalog meta-test can enforce it. Research: `epic-02-data-and-tenancy/research.md §R8`.

## Decision drivers
- Isolation that holds even when application code is wrong (defence in depth).
- Pooled connections must never carry tenant context from one request to the next.
- One mechanical convention that a test can check.

## Considered options
1. Schema-per-tenant
2. Database-per-tenant
3. **Shared tables + RLS on `tenant_id`**, with the tenant set per transaction

## Decision outcome
Chosen option: **3** (already locked by AGENTS.md). The concrete conventions:

**Roles** (created by `deploy/db/init/01-roles.sh`, which runs once per database as a superuser or DBA):

| Role | Rights |
|---|---|
| `memo_migrator` | Owns schema `memo`; used only by Flyway. |
| `memo_app` | `LOGIN NOSUPERUSER NOBYPASSRLS`; DML only, granted through default privileges; owns nothing. |
| read-only ops role | Not created in Phase 0. It needs a justified use case (Phase 7 support tooling) and will come with its own ADR. |

**Tenant tables:**
- Column `tenant_id uuid NOT NULL` (first column after `id`).
- `ALTER TABLE … ENABLE ROW LEVEL SECURITY; ALTER TABLE … FORCE ROW LEVEL SECURITY;`
- Exactly one tenant policy:
  ```sql
  CREATE POLICY tenant_isolation ON <table> FOR ALL
    USING      (tenant_id = (select nullif(current_setting('app.tenant_id', true), '')::uuid))
    WITH CHECK (tenant_id = (select nullif(current_setting('app.tenant_id', true), '')::uuid));
  ```
  The `nullif(…, '')` is the only deviation from the literal form in AGENTS.md §3.2. A reset setting is `''` on pooled connections, which would raise an error only *sometimes*. With `nullif`, a missing tenant **always** yields zero rows and rejected writes. The sub-select keeps InitPlan (evaluate-once) behaviour.
- `tenant_id` leads every multi-column index. Every foreign key has an index whose leading columns are the FK columns. Within tenant data, FKs are composite (`tenant_id, id`), so a row can never reference another tenant's row.
- Primary keys are UUIDv7 generated by the application (`IdGenerator`, backed by FasterXML JUG).

**Platform tables** (no `tenant_id`, e.g. `system_info`) are allowed only for non-tenant data. The tenant registry `tenancy_tenant` is a special case: it has RLS on `id` with the same expression, so a tenant can see only its own row.

**Views** must be created `WITH (security_invoker = true)`. **Functions** must not be `SECURITY DEFINER` unless the meta-test allow-lists them with a reason.

**Tenant context in the application:**
- `TenantTransactions.inTenant(tenantId) { … }` opens a transaction (or joins an existing one for the same tenant) and runs `select set_config('app.tenant_id', ?, true)`, which is transaction-local and never session-level.
- Tenant-scoped data access goes through `TenantDsl.current()`. It throws `MissingTenantContextException` when no tenant transaction is active: the loud application-level fail-closed. The database policy is the silent second line of defence.
- Joining a transaction that is bound to a **different** tenant throws.
- Phase 1a adds the request filter and propagation into jobs and listeners on top of this helper.

**Table naming:** tables are prefixed with their owning module identifier (`tenancy_*`, `system_*`); the meta-test checks this.

### Consequences
- Good: isolation is enforced in the database and can be checked mechanically. Context cannot leak through the connection pool.
- Bad: every tenant query pays the policy predicate. The cost is negligible with `tenant_id`-leading indexes and InitPlan evaluation, and it is verified with `EXPLAIN` per list query from Phase 1a.
- Follow-ups: the platform admin path (cross-tenant listing) needs a separate audited role (Phase 1a or Phase 7).

### Confirmation
- `RlsMetaTest`: catalog scan for every rule above.
- `CrossTenantIsolationIT`: read, list, update, delete, join, view and function.
- `RlsNegativeIT`: with RLS disabled, the same probes **do** leak.
- `TenantTransactionsTest`: fail-closed behaviour.
- A source-scan test forbids session-level `SET` and `set_config(…, false)`.
