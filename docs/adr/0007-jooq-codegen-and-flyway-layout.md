# 0007 — jOOQ edition, code generation pipeline and per-module Flyway layout

## Context and problem statement
`AGENTS.md §2` locks jOOQ (typed SQL) and Flyway migrations per Modulith module. We need code generation that reproduces the real schema exactly and works the same locally and in CI. Research: `epic-02-data-and-tenancy/research.md §R6, §R7`.

## Considered options
- Codegen:
  - **A.** Gradle plugin + Testcontainers at compile time
  - **B.** `DDLDatabase`
  - **C.** a third-party Testcontainers plugin
  - **D.** committed sources, regenerated by a test that boots the app
- Flyway:
  - one global folder;
  - **Spring Modulith per-module migrations**.

## Decision outcome
- **jOOQ Open Source Edition** (Apache-2.0). It supports the current PostgreSQL major, which is all we run. If a customer requires an older PostgreSQL major, that is a commercial-edition decision with its own ADR.
- **Codegen: option D.**
  - `JooqCodegenTest` boots the application against Testcontainers PostgreSQL (real role script, real Modulith Flyway ordering).
  - It runs `GenerationTool` (Kotlin generator, schema `memo`, Flyway history tables excluded) into a temporary directory and compares the result with `backend/src/main/jooq`.
  - In normal runs it fails on any difference. `./gradlew :backend:updateJooq` rewrites the directory.
  - The generated sources are committed and excluded from ktlint and detekt.
- **Flyway:** `spring.modulith.runtime.flyway-enabled=true`.
  - Global, rarely used objects go in `db/migration/__root`.
  - Each module's tables go in `db/migration/<module>`, with its own history table.
  - Versions are scoped per module.
  - Flyway connects as `memo_migrator`.

### Consequences
- Good: compilation and IDE sync need no Docker. The generated code always matches the migrated runtime schema. Schema changes show up as reviewable diffs.
- Bad: a developer must run `updateJooq` after changing a migration. The drift test fails with that instruction.
