# E03 Definition model and runtime — log

## 2026-11-11
- Plan written under the delegated gate (Phase 2 Q1): research (R1, R4, R5, R10, R11), ADR-0038 (definitions, lifecycle, migration), ADR-0039 (CEL conditions), design, threat model, tasks, test plan, UX review notes. Implementation starts with T1 and T2.
- Choices worth knowing: sub-workflows are inlined at publish (no child instances, so the one-instance-per-subject rule of E01 holds); loops are not edges (going back is the send-back action); review steps record **Recommend**, approve steps **Approve**, so the history says which one a person did.
- **T1 + T2 (definitions and conditions):** `workflow.definition` holds the schema-2 model, JSON parsing and printing, the validator (JSON Schema draft 2020-12, then the semantic rules with JSON pointers) and the compiler (schema-1 upgrade, fragment inlining in two passes so a call may follow another call). CEL 0.15.0 runs on the planner runtime (`standardCelRuntimeBuilder` is deprecated); comprehensions are off, so macros fail to compile; the planner needs heterogeneous numeric comparisons on. `WorkflowSubject` gained `attributes` and `attributeValues`; the memo offers `memoTypeId` and `classificationRank`. Fuzz targets for conditions and definition bodies join the nightly Jazzer job. The licence check maps "Go License" (RE2/J) to BSD-3-Clause.
- **T3 (runtime on compiled definitions):** migration `workflow/V3` carries every schema change of E03 at once (expand only) so later slices need no further migration. `Rounds` walks the compiled definition (route, review, approve, branch, notify, escalate-to-forum, end); route entries keep E01's pending steps so a round still shows who comes next. The engine takes the definition in `Transition` (default: the built-in), so E01's tests run unchanged. The writer inserts steps activated during an action before their tasks; follow-up actions (`ROUTE`, `NOTIFY`, `ESCALATE_TO_FORUM`) are written after the action with their details. `CompiledDefinitions` caches published versions by id (immutable, so no eviction). Memos now start on their type's definition key. The invariant property excludes `CANCELLED` from its coverage until T6 adds cancellation.
- Watch: the Arabic message catalogue is at 14.1 KiB gzip of its 15 KiB budget; E03's screens and E04–E06 will exceed it. Decide in T10 (split the catalogue per route, or raise the budget with a recorded reason).
- **T4 (parallel steps):** one rule covers the three modes: a step needs `all`, one or `n` approvals, is approved as soon as it has them and rejected as soon as it can no longer get them (`Parallel.verdict`). A return, or a rejection that ends the round, cancels every open task; a settled step cancels its leftover tasks. Simultaneous final approvals are serialised by the instance row lock (E01): the second finds its task cancelled and is refused, so a step settles once. Checked by a property against an oracle written from the design's rule table (1,000 cases over every mode) and two ITs (2-of-3, and the race).
- **T5 (task actions):** send back, forward, delegate, ask/answer, refer/opinion in the engine (`HandOns`, checked by `Guards` and `HandOnGuards`), with the step's offered actions and mandatory remarks enforced. Tasks gained a kind (decision, opinion, clarification), a delegated-for holder, a waiting flag and a parent. A delegate's action records `acting_for_id` from the task, not the session. A send-back cancels open tasks, skips pending route entries and runs the target step again (route entries restart with the rest of the route behind them). Public API: the hand-ons are a separate facade, `WorkflowHandOns`, beside `Workflows`; `WorkflowQueries.myTask` tells the memo view what the holder can do (role, waiting, delegated, positive action, offered actions, send-back targets). The memo endpoints `POST /api/v1/tasks/{id}/{send-back,forward,delegate,ask,answer,refer,opinion}` are in matrix `p2-e03-workflow.yaml`. Step-up stays on approvals only: a review step's Recommend does not ask for it. Audit action names use underscores (`workflow.task.sent_back`, `…opinion_given`): the audit store refuses hyphens.
- **T6 (round control):** recall (initiator, only while every task of the round is an untouched open decision; the memo returns to the initiator) and cancel (any status but terminal ones, reason required, `workflow.instances.cancel` with step-up at `POST /api/v1/admin/workflow/instances/{id}/cancel`, next to E01's `/admin/workflow/tasks`). Memos gain a `CANCELLED` status (migration `memo/V2`) in the closed box. `resume` restarts at the step that returned the item (a route entry at that approver's place in the new route); `skip-unchanged` carries approvals of the previous round made on the same subject snapshot as `CARRY` actions by those people (computed by the runner from the action history; parallel steps always run again, recorded in the design). The memo view offers Recall only when the workflow says it is recallable. Static analysis pushed three splits: hand-on and round-control commands dispatch through `HandOns.apply` and `RoundControl.apply`, branch evaluation moved to `Branches`, carry-over to `Carries`, and the holder's view of a task to `TaskDescriptions`.
- **T7 (definition lifecycle):** `/api/v1/admin/workflow-definitions` with list, read, create, new draft, replace, validate, submit, approve, send back, retire and export. Reading needs `workflow.definitions.manage` or `.approve`, so `@RequiresPermission` gained `orAnyOf` (checked by the interceptor before the path is bound). Maker-checker is a service rule (`SAME_PERSON`) backed by the V3 CHECK; submitting clears the previous reviewer so a reviewer can later author. Approval validates again (a fragment may have been retired meanwhile), inlines fragments and stores the compiled body, retiring the previously published version in the same transaction. A definition in use by a memo type (active or not) cannot be retired: the memo module answers through `WorkflowDefinitionUsage`. Deviations: a small migration `workflow/V4` after all, for a row `revision` (the `If-Match` of draft edits; submit takes it too, so a reviewer sees what was validated) and a unique index allowing one draft or version in review per definition; new drafts are audited as `workflow.definition.draft_created`; version numbers are read from the path as text, so a non-number is a 404 after the access and step-up checks rather than a 400 before them. Memo types now choose a published definition and a route policy that fits it: `INITIATOR_DEFINED` and `BOTH` need a `route` step, `FIXED` needs none, and memos of a `FIXED` type are submitted without a route; the two routed policies differ only in what the form shows (T10). Fields left out of a memo-type edit keep their values, so the E01 form cannot reset a type to the built-in definition. Tests: `DefinitionLifecycleIT` (HTTP: state machine, maker-checker, step-up, If-Match, built-ins, retire while in use, a `FIXED` memo end to end), `VersionPinningIT`, matrix rows.
- **T8 (in-flight migration):** `POST …/{key}/migrations/preview` lists instances running or returned on other versions of the definition (or the listed ones, at most 500) with what stops each one; `POST …/{key}/migrations` moves up to 100 listed instances in one transaction, with a step-up and an `Idempotency-Key`. The engine owns the rule (`Migrate` command, `Migrations.refusal`): a running instance may move when every active or pending step exists in the target with the same type (a route entry needs a `route` step); a returned one always may. The runner checks, under the subject and instance locks, that the instance is still on the version the caller saw (`VERSION_CHANGED` otherwise), records `MIGRATE` with the from and to numbers, audits `workflow.instance.migrated` and re-pins the instance. Both endpoints answer with the instances as they are, so a replayed key needs no stored result (the idempotency result column holds 2,000 characters, too little for 100 outcomes). The admin view of a subject (title only when cleared) moved to `AdminSubjects`, shared with the reassignment list. Tests: `MigrationIT` (preview reasons `STEP_CHANGED` and `STEP_MISSING`, only migratable instances move, replay, step-up, the migrated instance follows the new path and the other the old one), matrix rows.
- **T9 (events and history):** `WorkflowStepCompleted` (each step that holds tasks, when it becomes done) and `WorkflowInstanceEnded` (published last, after `WorkflowActionTaken`, so listeners see the subject updated) join E01's events; `WorkflowEscalated` is defined for E05. All carry the tenant and ids only. The memo answers `WorkflowNotifyRequested`: a recipient cleared for the memo becomes a participant of a new kind, `NOTIFIED` (migration `memo/V3`), so the link opens the memo, and gets `MEMO_UPDATE` (email and in-app, en/ar); someone not cleared is told nothing. The email says only that the memo reached a step that keeps them informed: the definition's message key goes with the in-app notification but is not shown, as E03 has no catalogue of tenant messages (E06's editor can add one). History entries now carry the action's details and the name of the step they concern (resolved against the pinned version); the memo history shows `step`, the people a task was handed to (`to`, by name) and the remaining details (branch inputs and result, message key, forum, migration versions). `current_step_name` was already kept by T3. Tests: `WorkflowEventsIT`, `MemoNotifyStepIT`.
- **T10 (web):** the Arabic catalogue would have passed its 15 KiB budget, and the size script says to split rather than raise it, so catalogues now load per part (`src/i18n/catalogue-parts.json`): `admin` (messages under `admin`, `access`, `users`, `mail`, `workflowTasks`, `memoTypes`, `workflows`) loads with `/admin` pages, `platform` with the operator console, `patterns` with the gallery, `core` with everything. A Vite plugin builds each part as its own chunk from the one authored catalogue per locale (`messages/<locale>.json?part=`), so translators and `i18n:verify` keep one file; the size check measures each part (Arabic core 8.5 KiB, admin 6.8 KiB). Pages under a part wait for it (`CatalogueGate`) instead of flashing English; English loads nothing, as its messages are the source messages in the code, which also takes the English catalogue out of the main bundle. Screens: `/admin/workflows` (definitions with their published and open versions, new definition) and `/admin/workflows/$key` (versions; the chosen version's body in a JSON editor with problems by pointer; save with If-Match, check an unsaved body, submit, import a file, export; approve, send back and retire for reviewers, with step-up; migration preview and move for reviewers). The visual editor is E06's, on the same API. Memo types choose a workflow and who chooses approvers (from `GET /api/v1/admin/memo-types/definitions`, so memo-type managers need no definition permission); a `FIXED` type's memos show no route section and offer no route editing. The memo view offers every action the step allows (Recommend, Send back with the step to go back to, Forward, Delegate, Ask, Ask for opinions with up to ten people, Answer, Give your opinion, Recall), names the holder's step and role, and says when the holder waits for an answer; the history names steps, the people a task went to, branch inputs and migrations. Inbox rows show the step and whether a task asks for an opinion or an answer (`InboxItem.kind`, `.stepName`). Web unit runs flaked a few times while the backend suite loaded the machine (different tests each time, all passing alone); seven of the last eight full runs were green. Watch CI.

Written by the demo admin and approved by the org admin through the real lifecycle (`WorkflowSeeding`), and chosen by a `FIXED` memo type of the same name (`MemoSeeding.fixedType`); seeded once at start-up, never stopping it. - **Epic summary:** definitions are tenant-authored JSON (schema 2) with CEL conditions, validated, reviewed by a second person and published immutably; instances pin a version and can be moved to a newer one where their open steps still fit; the engine adds review, branch, parallel (all, any, n of m), notify and escalate-to-forum steps, the hand-on actions, recall, cancel and two resubmission policies, all in the pure transition function with the E01 invariants kept. Deviations from the plan are recorded per slice above (migration `workflow/V4`; `orAnyOf` on `@RequiresPermission`; version numbers as path text; message catalogues per route).
