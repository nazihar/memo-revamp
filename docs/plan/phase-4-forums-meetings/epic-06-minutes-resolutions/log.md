- **Choices that came from the research:**
  - **The decision is a structured record** with named dissent (optional reason), named abstentions, an optional vote and "took no part" derived from declarations and attendance: CGI §5.3.3–5.3.4, Basel ¶60, and Bangladesh Bank's requirement that dissent be "comprehensively recorded".
  - **Resolution numbers at the meeting's end, in agenda order:** no voids for corrections made in the room; the period is the meeting's date.
  - **Memos move on when the meeting is marked as held by default**, with "when the minutes are approved" per committee type: s.249 makes minutes the evidence of a decision taken at the meeting; SS-1 allows certified extracts before the minutes are signed.
  - **Two approval modes per committee type:** at the next meeting (CGI §6.3: "virtually all organisations") or by circulation then noted (CGI §6.3's ratification; SS-1's comment window where silence is consent).
  - **Chair review before circulation** (CGI §6) and a comment box for members rather than co-editing (OnBoard users email revised versions; BoardPro keeps editing during review).
  - **Approved minutes are never edited:** corrections annexed in a new record version (CGI §6.2; BoardPro locks confirmed minutes).
  - **The secretary's notes are not part of the record** (CGI §8.1: notes are discoverable and usually destroyed after approval; here they are kept, never deleted, and visible only to secretaries).
- **Changes from the overview, recorded in ADR-0065 and ADR-0066, to report to the owner:**
  - numbering shares the format code (`common.numbering`), not one counter service: resolutions get their own counter, as meeting numbers already do, and no memo number or table changes (overview risk R8 avoided);
  - minutes approval follows a fixed path per committee type, not the workflow engine: the next-meeting step is another meeting's decision, the comment window is not a task, and each reader needs their own redacted copy, which the engine cannot give.
- **Found while reading:**
  - `ForumSubmissions.decide` is in `forum.internal`; T2 publishes `ForumDecisions` (decide, defer at a meeting, refer at a meeting).
  - `WorkflowForums.decided` takes only a remark; T2 adds `details` so the note sheet can link the resolution without a memo migration.
  - The PDF/A pipeline is internal to the memo module; T7 publishes `RecordPdfs` as `ReportPages` already is.
  - `templating` supports sections and table-row loops but not repeated blocks; T2 adds block loops (poi-tl's documented behaviour) without changing memo templates.
  - The meeting module cannot depend on minutes; E04's "declarations on a decided item change only by correction" goes through a `DecidedItems` port the minutes module implements, as E03's `PaperExclusions` hook did.
- **Uncertain until T1:** whether ONLYOFFICE 10.0.0.1 keeps a locked, tagged block-level content control through editing, undo and save. ## 2026-11-19 — T1 spike: content controls, block loops, review mode, shared numbering
**Result: ADR-0066 option B1 holds.** ONLYOFFICE 10.0.0.1 and Microsoft Word keep the locked, tagged item controls; the heading-style fallback (B2) is not needed. The structure check and "Restore item n" stay as the safety net (T5).

- **How it was tested.**
  - The draft: the sample minutes template (`testsupport/MinutesSample`: heading, attendance row loop, the `items` block with a declarations section, the key points, a vote row loop and the outcome, a closing line) filled for nine items, each in a control `memo-item:<id>`, title "Item n", `sdtLocked`. Item 5's discussion carries a canary.
  - ONLYOFFICE: the pinned image as in `ci/e2e-stack.sh` (JWT on, plugins off, the hardened `local-production-linux.json`), driven in Chromium by `web/e2e/spike/minutes-controls.spec.ts`. A small server in the spec serves the editor page, the file and the callback; saved files come through the callback (force save, status 6, and the closing save, status 2). `MinutesControlsRoundTripIT` (env-gated like the other spike ITs) writes the draft and checks the saved files with the StAX scan.
  - Three runs gave the same results. A force save sent right after typing sometimes answers error 4 ("no changes"): the editor sends changes to the server in batches; the closing save always carried them.
  - Word: the draft opened through COM automation, the deletions tried, a line typed in item 5, saved with personal information removed; kept as the golden file `templating/minutes-saved-by-word.docx` and checked in `ContentControlWrapperTest`.
- **ONLYOFFICE 10.0.0.1, edit mode:**
  - typing inside item 5's control and outside every control (the first line, the closing line) works; the edit stays inside the control;
  - a selection from item 6's heading into item 7, then Delete: **nothing is deleted** (silently; no message);
  - select all, then Delete: **nothing is deleted**;
  - Backspace at the start of item 7's control deletes the last characters of item 6's text, but neither merges nor removes a control; Delete or Backspace inside a control edits its text normally;
  - undo (Ctrl+Z) undid typing only; no control was ever removed by undo. The forum report (a locked control removed with Ctrl+Z) concerns controls a plugin adds during the session; ours are in the file when it opens;
  - force save, closing save, and a save after reopening the saved file: **nine controls each time, with tag, alias (title), id and `sdtLocked`**. ONLYOFFICE adds `w15:appearance boundingBox` to each control's properties and shows the title as a tab on hover.
- **Review mode** (`permissions.edit = false`, `permissions.review = true`, mode edit): the chair's typing is saved as `w:ins` and a deleted phrase as `w:del`, each with `w:author` (the editor config's user name), a date and an extra, non-standard `oouserid` attribute. A deletion spanning item 6's control is refused in review mode too. The controls are kept. `w:trackRevisions` stays off in `settings.xml`: review is enforced by the permissions, not by the file, so the secretary's own edits are not tracked (as designed).
- **Microsoft Word** (Microsoft 365, this machine): the nine controls appear as locked rich-text controls ("Content control cannot be deleted" on, "Contents cannot be edited" off). `ContentControl.Delete` answers "This content control is locked and cannot be deleted"; deleting a range around a control answers "The range cannot be deleted". Tags and locks survive save and reopen.
- **Copies:** replacing item 5's control with a generated block (heading, "You declared an interest in this item and took no part.", the outcome) and converting with ONLYOFFICE (`/converter/from-file`) to PDF and to PDF/A leaves no word of item 5's discussion in either text layer (PDFBox); the full document's PDF has it. The PDF/A copy passes veraPDF 1.30.3 as PDF/A-2u.
- **Block loops (poi-tl 1.12.2):** a `{{?items}}…{{/items}}` section over a list repeats once per element (poi-tl copies the body elements between the two tag paragraphs per element). Inside, value tags, a nested `{{?item.declarations}}` section and an `{{item.votes}}` row loop resolve against the element, then against the document's values. Empty list: the block disappears. One level only. Tags or markup in values stay text.
  - Kept as code: `TemplateData.blocks` and `TemplateData.control` (`ControlMark`) in `templating`; the scanner and `TagVocabulary.blocks` are T2.
  - **Constraint for T2:** a block with controls needs its `{{?items}}` and `{{/items}}` each in its own paragraph of the body (not in a table cell, not one paragraph); the fill fails otherwise, so the scanner must report it.
- **Controls by POI 6.0.0:** wrapping by moving nodes with XMLBeans cursors made the save quadratic (5.2 s for 60 items with long notes, over the fill's 5 s limit). The kept design: the filler adds a marker paragraph at the start and end of the block (a random token per fill, so no value can pass for one); after poi-tl writes the file, one StAX pass over `document.xml` turns each pair into a `w:sdt` and drops the markers. 60 items of 1,700 words (206 pages, 211 KB) fill in about 0.4 s.
  - `DocxControls` (published by `templating`): `scan` (StAX, no DTD or external entities, bounded like POI's packages), `replace` (one control's content, its properties kept) and `restore` (a missing control copied from a fresh fill after the previous item's control; refused when the copied content refers to package parts).
  - **StAX scan of the 206-page file: 9 ms** (budget 2 s). It reports duplicated, unknown and nested (inline) controls, so the structure check (T5) only has to compare tags.
- **Numbering:** the pure format code moved to `com.memo.common.numbering` (`NumberFormat`, `FormatPart` with `Code(name, varies, maxLength)` for the caller's codes, `NumberFormats.period/render/skeleton/problems`). `memo.internal.NumberFormats` keeps its API and maps memo's parts to it; `NumberReset` and `FinancialYearStyle` are type aliases, so JSON, OpenAPI and stored numbers are unchanged. Memo's numbering suite passes unchanged; an architecture rule checks the delegation and that the shared code is pure.

  - after `replace`, comments or footnotes referenced from inside the replaced control would still be in their parts of the package; copies are served as PDF only, and T6 already refuses copies while comments or tracked changes are unresolved and resets the document properties. T6 should also drop the comments, footnotes and endnotes parts' entries for replaced items (or refuse items with them);
  - the test plan's Testcontainers `MinutesControlsRoundTripIT` cannot drive the editor from the JVM; the nightly coverage of the round trip is the `minutes-approval.spec` journey (T11) on the stack, and the spike harness stays in `web/e2e/spike/` to re-check a new ONLYOFFICE version before it is taken.
