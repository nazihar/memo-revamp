# E06 Legacy import — threat model

> Step 4 of `AGENTS.md §5`. STRIDE over the new data flows, with mitigations mapped to OWASP ASVS 5.0 requirement areas. Builds on the E02 threat model (uploads, conversion, Tika), E03 (the access rule) and E04 (records, fixity). Decision: ADR-0055.

## Data flows
1. **Sources:** admin (`memo.import`) → `POST /files?purpose=imports.source` → upload pipeline (clamd, detection, `ZipInspector`, encryption) → `work` bucket → binding to the batch.
2. **Originals:** admin's browser (folder pick, one file at a time) → register paths → `POST /files?purpose=imports.intake` → upload pipeline (+ Tika server subtype for OLE2) → `work` bucket → intake entry.
3. **Dry run:** job → decrypt source → POI or Commons CSV on the parse pool → staging rows → validators in `READ ONLY` transactions → problems and mappings (staging).
4. **Import:** admin + step-up → job → staged original decrypted → full pipeline again (`copyFrom`, expected SHA-256) → `records` bucket (purpose `memo.legacy`) → one transaction: memo, legacy facts, participants, bindings, `memo.imported` audit → search rows → renditions (ONLYOFFICE, Tika) later.
5. **Verify and report:** job → re-hash originals → report parts (PDF, XLSX, manifest) → `records` bucket (purpose `imports.record`) → `import.batch.completed` audit → download by cleared readers.
6. **Afterwards:** readers → memo view, search, originals' previews; holders of `memo.import` → corrections and classification raises; weekly fixity; purge of staged copies.

| S2 | An upload is bound to another batch or tenant by forging the owner id | 1, 2 | The purpose parses the owner (`{batchId}:{table}` or an intake id) and checks, in the tenant's transaction, that the entry exists, its batch is OPEN or VALIDATED and the actor holds `memo.import`; RLS on every table; ids are random UUIDs | V8.2, V8.4 |
| S3 | A forged job payload runs an import in another tenant | 3, 4 | Tenant and actor bound from the task data (ADR-0018); every read and write in a tenant transaction under forced RLS; no tenant, fail closed | V8.4, V15.3 |
| T1 | The workbook or an original changes between the dry run and the import | 3, 4 | The input hash covers sources, originals (path, SHA-256), mappings and settings; any change moves the batch back to OPEN; start needs VALIDATED and the row count shown; the sources used are copied as records at start | V2.3, V16.4 |
| T2 | A staged original is corrupted or swapped at rest | 2, 4, 5 | SHA-256 at intake; promotion re-hashes and refuses a mismatch before storing (`copyFrom` with the expected hash); the verification pass and the weekly fixity job re-read stored originals; mismatches audited and alerted | V5.3, V16.4 |

| I1 | **Cross-tenant:** a batch, its staging rows, problems or report seen by another tenant | all | `tenant_id` and forced RLS on every new table; purposes check the tenant's own rows; cross-tenant tests on every new table and endpoint | V8.4 |

| D2 | **Hostile CSV:** a giant quoted field, endless lines, invalid UTF-8, a UTF-16 BOM | 1, 3 | 20 MiB cap; strict UTF-8 decoder; row caps through `setMaxRows`; 32,767 characters per value; lenient modes off; Jazzer | V5.2, V2.2 |
| D3 | **Resource exhaustion** by volume: thousands of uploads, a huge batch, the rendition backlog, scanner load | 2, 4 | Intake rate limit (600 a minute) and the per-node upload semaphore; caps on originals (200,000) and bytes (200 GiB) per batch; at most 5 open batches and 1 running import per tenant; the import waits while 200 renditions are pending; chunks of 50; the conversion caps of ADR-0045 | V15.2, V2.4 |
| D4 | **Hostile OLE2, RTF or TIFF originals** exploit a parser | 2, 4 | Never parsed in the backend JVM: clamd scans (macros refused as `Heuristics.OLE2.ContainsMacros`, encrypted refused); the subtype comes from the isolated Tika server; renditions only in ONLYOFFICE and the Tika server, with no network, CPU and memory limits and time limits (ADR-0045, ADR-0047); `.msg` and unknown OLE2 refused | V5.2, V15.2 |
| E1 | A legacy person gains read access to memos they should not see | 4 | Linked only through a confirmed explicit identifier; linked people are the legacy initiator and approvers, who had access in the legacy system; clearance always applies; the people mapping and its confirmations are audited | V8.2, V8.3 |
| E2 | Legacy formats leak into other purposes (an OLE2 attachment on a native memo) | 2 | A purpose flag only `imports.intake` and `memo.legacy` may set, checked by an architecture test and at start-up; `memo.attachment` stays as it was | V5.2, V15.3 |
| E3 | Zip slip or path traversal through relative paths | 2 | The server never extracts and never builds a filesystem path from a name; paths are metadata, validated (no `..`, no leading `/`, no control characters, NFC) | V5.3 |
| E4 | The import's system actor is used to write other files | 4, 5 | `memo.legacy` and `imports.record` allow uploads only by `System("legacy-import")`; the job reads only its batch's staged versions | V8.2 |

## Residual risks
- **POI parses the workbook in the backend JVM.** It is an admin-supplied file behind a privileged permission and a step-up for the import, but a parser bug could still affect the node. The limits, the single-thread pool, the timeout, the catch-all and fuzzing reduce it; a separate process is the next step if fuzzing finds crashes that escape the catch-all.
- **Legacy Office formats are now accepted** in two purposes. Their safety rests on clamd's OLE2 macro heuristic, the Tika server's typing and ONLYOFFICE's isolation. A macro hidden from clamd would be stored, but never run by us: ONLYOFFICE runs no macros (ADR-0047), and downloads are attachments with strict headers.
- **Legacy facts are only as true as the legacy system.** The import cannot verify that a legacy approval happened; it says so on every imported memo.
- **Files promoted for a row that then fails** (a reference race between the pre-check and the commit) remain stored as locked records under an unused memo id. They are listed in the report as "stored, not bound"; the expected count is zero.
- **A linked person who was never cleared** keeps a participant row that grants nothing (clearance applies). The report lists linked people per row.
- **The browser carries the volume.** Very large migrations need the command-line uploader, which is not built; the runbook says when to ask for it.
