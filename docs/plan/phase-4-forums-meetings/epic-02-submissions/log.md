- One change from the overview: a decision follows a fixed mapping (approve or noted continues, reject rejects, return or decline returns). The overview also offered a CEL attribute to branch on the outcome; that is deferred, because no source needed it.
- T1 (the waiting forum step) merged in #159; T2 (submissions and triage) merged in #160. CI on #160 found that `DefinitionRuntimeIT` escalated to a committee its tenant never had; the test now creates it, since an escalation to an unknown committee is refused (`FORUM_INACTIVE`).
- T3 (readers and the memo side), with these differences from the design:
  - **No system note kind.** A committee's return or decline is already a workflow action with the secretary as actor and the reason as its remark, and the note sheet already lists such actions. The note sheet entry now also carries `committee` (the name) and `committeeOutcome`, so it reads "Returned by the Management Credit Committee: reason". A second, system-written entry would have recorded the same thing twice.
  - **The submission policy got its own migration** (`forum/V4`), not a V3 column: V3 had merged without it. Null reads as the defaults (5 working days, chair approval for late papers, a reminder after 5 working days).
  - **Committee readers are kept in step, not granted once.** `MemoReaders.syncForum` makes the memo's `FORUM` rows exactly the chair and secretaries in office of every forum with an open submission of the memo. It runs after every submission change and after a chair or secretary joins or leaves. A role that starts on a future date takes effect at the next change. `FORUM` is the weakest participant kind, so it never replaces a stronger row, and retiring it leaves other rows alone.
  - **"With the X committee"** reaches the memo through the workflow, not the forum module (`WorkflowForums.waitingOn`, names from `EscalationTargets`). This keeps the direction forum → memo and workflow.
  - **Fixed a T1 defect:** a step's `resolution` was written but never read back, so a reloaded waiting step had forgotten its forum. The forum's decision action then had no `forum` detail. Saving any changed step also blanked the resolution E04 records (who an assignee resolved to, and why). `InstanceStore` now reads it back.
- T5 (close, backend part):
  - **Demo:** "Credit under authority" gets a new version, maker-checked like the rest. After the credit desk, a branch on the proposal's amount sends BDT 5 million or more to the Management Credit Committee (`escalate-to-forum`, `wait: true`) before the delegation of authority; smaller amounts go straight to the authority. The seeder seeds the committees first and adds this version last, after the credit proposal type that brings `amount`. `WorkflowSeeding.revise` now revises the latest published version, not only a lone version 1. `DemoWorkflowsIT` walks both amounts through the simulator.
  - **Validation fix:** when two subject types offer one attribute name with different types, a definition's declared type now counts if any of them offers it. Before, the last subject type registered won, which in tests made the memo's `amount` (a double) clash with the test subject's (an int).
  - **Performance** (`SubmissionPerformanceIT`): 50,000 submissions, 2,000 open in one queue. Queue (500 rows with names and readable memos): p95 44 ms against a budget of 150 ms. A memo's submissions: p95 10 ms against 50 ms. Both use an index.
  - Runbook `committees.md`; four ASVS rows (V8 ×2, V2, V16).
  - **Moved to T4:** the journey `committee-escalation.spec` drives the queue screens, which wait for the owner's review of flow M with E03. A seeded paper in the demo queue moves there too: seeding one needs memo field values, which the seeding API does not take yet.
